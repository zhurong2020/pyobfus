（数字生命卡兹克，标注日期 2026-10-12）。本文保留其论点摘要，不复制文章全文。

## 3. 威胁模型：分别评测三条路线

| 路线 | 攻击者掌握的信息 | 可衡量的结果 | pyobfus 边界 |
|---|---|---|---|
| 静态实现恢复 | 交付文件、源码／字节码／常量；无私有 mapping 与外部密钥 | 功能重建、资产提取、所需预算 | 混淆与密文可影响静态暴露，具体增益待测 |
| 可运行交付物分析 | 可执行产物、工具、运行反馈；分别区分未授权与已授权环境 | 迭代重建／提取成本 | 授权运行可能暴露解密后内容，不能只用静态实验推断 |
| 黑盒功能重实现 | 公共接口、文档、受限输入输出查询；无内部代码 | 行为近似、隐藏边界测试通过率 | 可能完全绕过代码保护，不能称为破解保护层 |

加密、授权与业务安全分开讨论。外部密钥减少随包直接交付解密材料的情况，
不保证合法运行主机不能取得运行时明文。服务器逻辑同样可能被黑盒学习。
开发者拥有私有 mapping 的调试流程与外部攻击者分离，不能为加强保护破坏正常支持能力。

## 5. 候选 A：Community 交付物检查与覆盖报告

用户：交付离线 Python 应用的个人开发者与小团队。
问题：构建成功不说明最后打包的文件正确，更不说明指定保护实际覆盖。
证据：仓库已有打包／mapping／runtime 边界，真实离线交付需求，以及 opacity 的明确范围限制。

第一版范围建议：**交付目录与 wheel**；wheel 是应用依赖／runtime 载体，不改变离线应用优先的选择。
用户明确声明需保护的模块／函数／资源和可公开接口，不从文件名臆测商业秘密。

候选检查：

- 已声明私有的 mapping、原始源码、调试／中间文件是否混入交付。
- 声明资产是否匹配构建计划，是否处理、跳过、按策略保留或无法确认。
- opacity 规则的匹配数量、实际动作、未支持对象及原因。
- runtime 要求与交付记录是否对应；离线可安装性需要另附实跑证据，静态检查不伪装为安装验证。
- 本次交付与构建证据的关系；第三方公开依赖与有意公开入口不按泄漏处理。

复用既有 JSON／reason codes／报告基础；现有 `status`、`ai_hint`、MCP `next_tool` 契约保持兼容。
命令名、schema、资产声明格式与报告粒度尚待复核和设计，不预先承诺新的 CLI 开关。
私有符号级记录与可公开报告分开，公开报告不得暴露源码、密钥、买家或许可证信息。

验收：维护的合成 fixture 能检出已知遗漏，正常交付不误报；
每项有证据与明确局限，结果区分未知与失败，报告不打印敏感值。
不生成未经校准的安全分数，不把字符串未检出解释为不可恢复，不默认执行目标。
凭据全面扫描交给 gitleaks 等已有工具，避免重复建设。

## 6. 候选 B：有预算的 Agent 重建实验

定位：扩展 P2-18 的研发实验，先决定技术取舍，不立即推出“抗 AI”预设或托管平台。

建议首轮：6–10 个自定义业务样例（具体数量待复核），至少一个小型多模块项目。
公共算法仅作能力校准，不能承担专有逻辑恢复结论。给模型家族、每条件重复次数与费用设上限。
先用原文／无保护对照检查任务与评分是否有效；各种保护配置记录真实生效范围和 no-op。

- 三条威胁路线分别报告，未授权／已授权运行也分别报告，不混合成单一恢复率。
- Agent 可见测试／反馈与最终隐藏评分测试分离；隐藏测试不进入工作区、上下文或工具输出。
- 固定模型标识、日期、提示、工具权限、预算、产物哈希、Python／工具版本和执行环境。
- 记录功能通过率、时间、尝试次数、工具轨迹、token／费用与失败原因；
  防御侧同时记录启动／运行开销、包体积、兼容性与调试影响。
- 隔离执行生成代码和目标，禁止网络／宿主状态访问，限制资源；沿用现有隔离基础，
  具体适配 WSL 与离线目标需复核。不得使用真实密钥、客户数据或开发者状态作为 fixture。
- 预算到期是“该预算内未成功”，不是不可逆；多样例／多重复才可支持汇总统计。
- 如果某变换无可测增益而兼容性／性能成本明显，则停止扩展该变换。

基础方法与本地验证不收费；真实模型调用是否执行、源码是否交给供应商、费用预算须单独明确。
本轮只授权规划与保存，尚未授权这些调用。第三方 REA 可作可选评测适配器候选，
不能因为热度就成为运行或评测的强制依赖。

## 7. 候选 C：Pro 选择性保护与密钥交付

用户／买家：有特有算法、规则或数据，必须交付到客户离线环境的应用开发者。
价值：资产保护与分发控制，不按项目大小收费。

先用覆盖报告暴露已有能力的实际边界；再从以下事项择一，避免同时扩张：

1. 依据客户代码扩展 opacity 的对象范围／层行为，先证明语义和调试不退步。
2. 有需求后为 Vault 接入应用 key provider，明确多资产密钥隔离、缺失／错误 key 行为。
3. 有明确资源类型需求后改善加密资源加载，不承诺自动保护所有模型／配置格式。
4. 优先证明受支持离线目标可安装、可运行、无原源码仍能复现行为，开发者能私下诊断错误。

离线交付不默认依赖远程 key server。线上授权、预置 key 与离线授权各自的生命周期、
续期／撤销能力和失败行为必须在设计中明确；纯离线副本不能承诺即时远程撤销。
轮换数据密钥通常涉及重新加密／构建；密钥包装等方案是后续设计，不能称当前已支持。
产品应明确客户的应用授权与构建器 Pro 许可是不同边界。

## 8. 候选 D：Pro 归因能力验证（后置）

先建立处理矩阵：原样复制、格式变化、改名、部分复制、编译／打包、
外部 key binding、解密后重写、AI 重实现。区分买家构建匹配、提取线索和无法判断。
验证现有恢复原语在各配置下的适用条件及误归因风险，必要时再改善买家构建记录与工具。

不承诺任意重实现仍可归因，不通过改变正常业务结果植入标记；
买家标识使用不含 PII 的内部 ID，归因记录保持私有，无默认回传。

## 9. Community / Pro 分层

| 能力 | Community | Pro |
|---|---|---|
| 正确性、兼容性、基本混淆与接口集成 | 完整提供 | 同一免费基础 |
| 本地交付检查、覆盖报告、mapping／unmap、provenance | 完整提供 | 可检查 Pro 保护状态，不能为查看结果另设付费门槛 |
| 基础本地验证与公开评测方法 | 免费 | 持续托管／专业评估可另议，当前无平台计划 |
| 核心函数、字符串、资源加强保护 | 客观建议与现有基础能力 | 实施增强保护 |
| 应用提供密钥、设备／期限／运行控制 | 不承担 Pro 保护执行 | 提供并验证 |
| 买家相关构建与归因 | 普通构建证据 | 商业归因能力 |
| 集中策略、KMS、审计留存、SLA | 本地原语保留 | 有重复团队需求后再议 |

不删除既有 Community 能力，不新增文件／行数限制，不把 correctness 或基本评估变成 Pro。
发现私有 mapping 混入交付应免费帮助修正；发现有价值资源明文交付可以提出移出客户端、
调整架构或 Pro 保护等选项，不能把全部发现变成升级销售提示。
公开方法／检查 Pro 产物不等于公开 Pro 实现，源代码与许可边界保持。

## 10. 顺序、解冻条件与实施 gate

| 阶段 | 最小结果 | 下一步条件 |
|---|---|---|
| R0：独立复核 | Claude 等 LLM 的反证、来源核查、代码现状审计与修订建议 | 维护者确认修订后的范围；当前尚未完成 |
| R1：现有质量主线 | 已有版本收尾、转换缺陷处理、设计状态对齐 | 按原计划独立批准与验证，不捆绑新路线 |
| R2：有限实验 | 候选 A 合成交付检查原型；候选 B 小样本协议与预算设计 | 原型能定位遗漏／实验能区分保护配置，且维护成本可接受 |
| R3：首个新用户功能 | Community 交付检查与覆盖报告 | 实际离线应用验证、有可解释误报与局限 |
| R4：单项 Pro 补齐 | 从候选 C 择一 | 明确客户／下游需求、支持环境与实验依据 |
| R5：后续扩张 | 归因、更多格式／团队服务等 | 重复需求与维护资源成立 |

R2 可独立准备，但不等于授权同时实施所有候选。没有预定版本号或硬性日程。
大规模新能力优先要求两个独立需求信号；单个真实下游可支持范围有限的修复／验证实验。
一个 LLM 的推荐、一篇文章或 GitHub 星数不能单独通过需求 gate。

实施前需完成：独立复核 → 维护者决定 → 单项设计（用户／买家／问题／证据／版本边界）
→ 最小范围及验收 → 实现与独立代码审核。合并、发版、部署沿用各自批准要求。

继续延后：native VM／通用二进制保护器、反沙箱规避、自动服务化、云端源码上传混淆、
复杂企业许可平台、按热度引入新预设。编译合作与离线支持验证可以推进，不等于自建编译器。
若评测显示核心逻辑能廉价黑盒重建，应如实建议调整交付／架构，而不是无限叠加 AST 变换。

## 11. 独立复核待回答的问题

- 离线应用优先的需求证据够不够？首次支持目标与格式是否应进一步收窄？
- 候选 A 与现有 check／report／packaging lane 的真实差距是什么，哪些无需新增功能？
- 无源码交付时，如何取得可信的覆盖证据，哪些只能由用户声明，哪些必须记为未知？
- opacity 四层的 CLI 补齐是否比 Vault 外部密钥更有价值？如何避免运行／调试语义破坏？
- 外部 key、离线授权、watermark 组合是否有现有冲突，用户应如何理解保护边界？
- Agent 实验如何避免公开算法记忆、测试泄漏、一次尝试与无效对照带来的假结论？
- 在当前采用量下，何种结果足以解冻新能力，何种结果应停止？
- 有无更简单的外部工具／文档／fixture 能解决问题，而无需新增 pyobfus 子系统？

### 13.2 修订后的候选范围

- **候选 A** 收窄为外部工具做不到的三项：已知私有产物（mapping、原文按 provenance 输入哈希、scrub 私钥）出现在交付目录或 wheel 中；
  交付文件与 build report 输出哈希的对应；回读 Pro 写出的处理事实。凭据与通用打包卫生只写组合命令文档
  （check-wheel-contents、gitleaks 等）。首版只覆盖「目录 + wheel」。
- **覆盖报告**：由 Pro 把 opacity 匹配／注入／跳过（含「规则只匹配到方法」）写进 build report，Core 免费读取展示，源码分离不变。
- **候选 B**：先写协议与零成本确定性脚本（「key 在包内」时读字面量即可解密，说明保护上限）；付费运行见 13.4。
- **候选 C**：删除「opacity 四层补齐」（只有 L3 有实现）；资源保护改为「embed-data 与 vault 接入 key provider」；
  「fusion × 目录构建」是多模块离线应用拿到 Pro 保护的前提，排在 C 的首位，需单独设计。
- **候选 D**：收窄为如实声明（只对原样或轻改再分发有效）+ 已加的组合警告；扩展推迟。
- **「离线」三档**写进交付文档：物理隔离（预置 key／签名授权，只能人工续期，不能远程撤销）、站点服务器（应用自己的 key server，正是 Y-3 provider 的用途）、间歇联网（宽限期）。
  pyobfus 只提供 key 接入原语，不做授权服务器；构建器 Pro 许可与客户应用授权分开写。

### 13.3 近期顺序

1. 0.7.0 随发 PR #93／#94（runtime 先发）。
2. 离线交付指南（公开文档，含 `--no-index` 安装 runtime、三档离线、外部工具组合、fusion 适用范围）——同时是扩大使用面的素材，可接 10-13 起的内容节奏。
3. 覆盖报告（Pro 写事实、Core 读）+ 收窄版交付检查原型，用合成 fixture 验证。
4. Agent 实验协议文档与确定性脚本。
之后再按需求信号决定「fusion × 目录构建」设计。
