## Release objective

Make the existing config-aware `pyobfus --check` findings visible in GitHub
Code Scanning and other SARIF 2.1.0 consumers without changing the current
text, JSON, MCP or exit-code contracts.

This is deliberately one demonstrable feature rather than a bundle. It gives
the release a new discovery path (SARIF, code scanning, pull-request review and
AI security review) while keeping regression and messaging risk small.

## User-facing contract

Recommended additive CLI:

```bash
pyobfus --check src/ --sarif pyobfus.sarif
pyobfus --check src/ --sarif pyobfus.sarif --json
```

- `--sarif PATH` is valid only with `--check`.
- SARIF is written to the requested file; normal text output remains on stdout.
- Combining it with `--json` keeps the existing pyobfus JSON report on stdout
  and writes SARIF separately. Existing JSON must be byte-shape compatible.
- The scan exit code remains `0` safe, `1` high-severity finding, `2` parse
  error. Writing SARIF must not turn findings into a new exit-code policy.
- `--offline`, config discovery, `--config`, `--preset` and `--no-config`
  behave exactly as they do for the existing report.
- Refuse a directory target and report file-write failures through the normal
  structured error envelope when `--json` is active.
- Use an atomic same-directory temporary file followed by replacement so CI
  never uploads a partially written result.

No `--format` switch is introduced in 0.5.21. A file option composes with the
stable text/JSON contract and matches CI upload workflows without creating a
third mutually exclusive stdout mode.

## SARIF v1 mapping

- SARIF `version`: `2.1.0` and the official 2.1.0 schema URI.
- Driver name: `pyobfus`; semantic version: the running package version.
- One rule for each existing stable preflight category. Rule IDs use the
  category strings already treated as public JSON identifiers, prefixed as
  `PYOBFUS/<category>` rather than inventing a second numbering registry.
- Severity mapping:
  - `high` -> SARIF `error`
  - `medium` -> `warning`
  - `low` -> `note`
  - `info` -> `note`
- Artifact locations are repository/input-root-relative POSIX paths only.
  Never emit absolute paths or `file://` URIs.
- SARIF columns are one-based. Convert the current zero-based AST column;
  preserve the existing one-based line.
- Results use category-level safe messages. Do not copy `snippet`, source
  literals, absolute paths, dependency index credentials, license state,
  mappings, buyer/device IDs or generated output into SARIF.
- `partialFingerprints` are deterministic hashes of a versioned tuple of rule,
  safe relative path and structural location. Document that v1 is stable for
  an unchanged finding, not across arbitrary source-line moves.
- Findings excluded by effective config may be included with an explicit SARIF
  suppression and `pyobfus.excluded=true`; they must not change scan exit code.
- Parse failures belong in invocation notifications, not invented source-risk
  rules. Set invocation success/exit metadata consistently with exit code `2`.
- Include `automationDetails.id` suitable for repeat CI runs, but no repository,
  branch, actor or remote URL collection.

## Code ownership

Add a small `pyobfus/core/sarif.py` projection layer. It consumes a complete
`PreflightReport`; it must not rescan source or independently recalculate
severity/category counts. This is the first practical step toward the shared
build-report fact model in the September research.

The CLI owns option validation and atomic file output. `preflight.py` remains
the source of finding facts and exit semantics. The MCP server and VS Code
extension require no schema change in this release.

## Tests

Minimum new coverage:

1. valid SARIF 2.1.0 top-level and run/driver shape;
2. all category rule IDs and severity mappings;
3. one-based region conversion;
4. deterministic fingerprints and documented line-move behavior;
5. config-excluded finding suppression without exit-code change;
6. parse-error invocation notification;
7. no source snippet/literal, absolute WSL/Windows path or secret-like field;
8. `--sarif` plus text and `--json` contract preservation;
9. invalid mode/path and atomic-write failure behavior;
10. schema validation using a pinned/local schema fixture or a deterministic
    validator dependency; tests must not need network access;
11. disposable GitHub Actions artifact/upload smoke test before release;
12. existing core, MCP, integration and VS Code real-contract suites remain
    green.

The first real upload smoke should use the pyobfus repository itself in
audit-only mode. It must not claim `baselineState=unchanged` without a complete
comparison and must not become a blocking gate in 0.5.21. The staged-bootstrap,
suppression and artifact-verification rationale is documented in
[SELF_DOGFOODING_BEST_PRACTICES.md](SELF_DOGFOODING_BEST_PRACTICES.md).

## Documentation and launch assets

- README example and a short `docs/SARIF_CODE_SCANNING.md` recipe;
- GitHub Actions example with least-privilege `security-events: write`, noting
  the entitlement caveat for private repositories;
- AI-oriented example explaining that SARIF is a review artifact, not proof
  that obfuscated output is safe;
- CHANGELOG entry, CLI help snapshot and `llms.txt` / `llms-full.txt` sync;
- one release-note screenshot or captured workflow artifact showing a real
  finding in code scanning;
- searchable release language: Python obfuscation preflight, SARIF 2.1.0,
  GitHub Code Scanning, AI-generated dependency review.

## Explicit non-goals

- no new obfuscation transform;
- no Community build-marker implementation in 0.5.21;
- no generalized build report yet;
- no SARIF upload, GitHub token handling or network call inside pyobfus;
- no changes to MCP tool schemas or VS Code diagnostics;
- no change to finding detection, severity, config mitigation or exit codes;
- no release solely because the target date arrives.

## Follow-on cadence (not bundled into 0.5.21)

Maintain visibility with a pipeline of small, meaningful releases rather than
empty churn:

1. **0.5.21 — SARIF preflight** (target 09-04/05).
2. **0.5.22 — protected-deployment safety** (candidate 3–5 days later): Python
   3.14 remote-debug startup advisory plus the absolute-path privacy fix for
   the existing Community header; scope must be designed before coding.
3. **0.5.23 — verifiable build report MVP**: only after its shared fact schema
   is approved; do not pre-commit a date.
4. **MCP 0.3.11** remains independent. Its current Registry-link metadata fix
   alone is too small to justify immediate publication; pair it with verified
   MCP conformance evidence or another real MCP-facing improvement.

Operational rule: aim for roughly two meaningful release opportunities per
week while the backlog supports it, normally leave at least 48–72 hours for
CI, indexing and download observation, and skip a slot when acceptance evidence
is incomplete. Record non-release-day download baselines so release/CI spikes
are not mistaken for retained users.
