# DEV 文章发布清单

用于后续 pyobfus 工程文章。2026-10-28 第二篇发布时，DEV 编辑器显示
Publishing Tips：封面图有助于首页与社交展示；发布后可分享给相关社区；
用具体问题邀请读者交流，并交代写作缘由。它们是提示，不是自动投稿、
必须配图或互动增长的保证。发布动作由维护者执行。

## 写作与技术核查

1. 先写读者能独立使用的问题、复现、结果和边界。使用已发布版本；
   将命令及预期输出在隔离环境重跑。不要把本地模拟说成平台服务端验收。
2. 标题用普通文本填写编辑器标题栏；正文从第一段开始，不重复标题。
   简介准确概括问题与可得答案；标签不超过四个，按主题选择。
3. 只放有直接上下文的源码、官方文档和旧文链接。不为了互链而加入
   不相关的前篇文章；首次在 DEV 发布时不设置外站 canonical URL。
4. AI 参与起草、校对或代码核验时，选择匹配的 AI disclosure 档位，
   保留简短的正文披露及验证范围；作者亲自审读并对事实负责。

## 封面与预览

1. 考虑与正文主旨直接相关的封面。DEV Editor Guide 建议 1000 × 420；
   简图优于装饰图，关键结论仍须出现在正文。没有合适图片可以留空。
2. Basic Markdown 编辑器可使用 front matter；Rich + Markdown 编辑器
   使用独立的标题、简介、标签和封面字段。发布前预览标题、封面裁切、
   代码块、GitHub Actions `${{ ... }}` 表达式、链接与正文末尾。
3. 若邀请评论，问一个正文确实提出的具体问题，例如读者遇到的失败
   模式与复现结果。说明自己为何写这篇；不要用空泛的互动口号。

## 发布后

1. 记录真实 URL、发布时间及其时区，并核对公开正文、标签、封面和
   AI 披露；本地定稿保存最终版本，历史草稿记录不改写。
2. 由维护者决定是否分享到 X、同事或相关社区。分享文案提供问题与
   可用结论；未实际分享的渠道保持“未核实/未发布”状态。
3. 约 24 小时、一周及月度复盘时分别观察 DEV 后台浏览、反应、评论，
   再看 GitHub 来源和 PyPI 安静日。区分发版、内容发布与其他流量，
   不把相关性写成因果，也不把公开互动数当成阅读数。
