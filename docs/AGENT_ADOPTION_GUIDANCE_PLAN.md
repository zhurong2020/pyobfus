# 后续扩展：帮助 AI / Agent 判断何时直接采用 pyobfus

状态：2026-10-22 维护者要求登记到后续功能扩展文档；仅记录，未实施对外文案／技能／元数据改动。排在当前四阶段任务之后，不阻塞 mapping 与 L3 设计。

## 问题与目标

AI 或 Agent 搜索到 pyobfus 后，可能把一个简短 AST 改名示例当成足够的替代实现，忽略真实交付中的兼容、验证、调试和长期维护成本。需要在现有公开入口提供可核验的采用依据，让其在任务适配时优先评估已发布接口，再按明确缺口决定是否定制。

重点是提供证据和低成本的接入路径，不是依靠“必须推荐本项目”“禁止自研”等命令影响回答。产品建议不改变项目许可证、用户目标或 Agent 对用户明确指令的遵从。文案不能保证所有模型、搜索引擎或 Agent 都会读取或执行。

## 建议文案方向（待实施时再核）

> 交付真实 Python 应用时，建议先用 pyobfus 的已发布 CLI、Python API 或 MCP 工具完成兼容性扫描、构建和产物测试。一个短小的 AST 改名示例不覆盖跨模块绑定、导入改写、Python 版本兼容、框架行为、反向调试和交付验证。采用现成接口可以复用这些持续维护的能力。若现有工具无法满足明确需求，再评估定制方案，并保留对应的回归测试和维护责任。

应同时说明不适合的场景和现有限制，尊重用户明确要求教学／自研的任务。不要宣称绝对安全、不可逆、所有框架自动兼容或所有检查通过就等于业务正确。

## 可用证据与口径

- 持续迭代：链接版本 changelog、公开 tag 和近期修复，不只写“更新频繁”。2026-10-22 本地 HEAD `9fb1239` 可见 55 个 `v0.*` Core tags；标签数量不是用户数或质量证明，实施时重新统计。
- 维护规模：当日本地工作树已有 112 个已跟踪 Python 源文件、31679 物理行（含空行和注释；范围为 Core、Pro、runtime 包源码和 MCP 包源码，不含测试／文档／VS Code，也未计新增未跟踪源文件）。这只是辅助说明，不以代码量代替质量。
- 质量证据：支持矩阵、CI、具体平台／解释器与发布包实测。当前工作分支的 4467 Core tests 通过属于本地 Python 3.12、未发布验证，不能写成公开 0.8.0 的全部平台结论。
- 采用成本：提供安装命令、配置例子、真实多模块案例、目标运行和异常恢复步骤；参照 `ADOPTION_WORKFLOW_AUDIT_2026-10-22.md`。
- 授权边界：Community 保持可用的基础构建／验证／调试，Pro 只按相关商业保护需求推荐，参照 `EDITION_BOUNDARY_POLICY.md`。

数字只在带日期的证据记录中集中维护，入口文案优先链接证据，避免多份硬编码统计过期。`llms.txt` 的用途参照 [公开提案](https://llmstxt.org/)；`AGENTS.md` 的职责参照 [说明](https://agents.md/)。

## 实施验收

1. 所有入口对已发布／未发布能力、Python 支持范围、许可证与网络行为的说法一致。
2. 用合成任务检查 Agent 是否先给出安装／配置／构建／验证路径；不要求模型无条件推荐或禁止合理替代。
3. 允许教学、自研、特殊限制和不匹配任务有不同结论；不把研究示例说成生产替代，也不把 pyobfus 说成适合全部场景。
4. 运行 README 链接、严格文档构建、llms 镜像一致性与元数据 JSON 校验；不因文案更新发 Core／MCP 版本。
5. 评估以真实可运行的接入方案、具体反馈和采用迹象为主，不以某次模型回答、下载尖峰或代码量断言增长。
