# P0：包根目录的模块属性兼容性（2026-10-28）

状态：修复与验证在开发分支完成，尚未发布。此记录描述 Core 0.10.0 之后的候选改动；不要把它写成公开 0.10.0 的能力。

## 复现与原因

原版 Core 0.10.0 将 Python 3.15 标准库 `json/` 直接作为输入目录构建成功，统计为 0 个未证明的模块属性访问；生成的 `json` 导入失败，报 `scanner.make_scanner` 不存在。包作为输入目录时，规划使用了 `scanner`、`decoder` 这类模块名，而源码中的绝对导入使用 `json.scanner`，故目标被误判为项目外。把包放进父目录再构建可报告 5 个未证明站点，但默认输出仍因保留 `scanner.make_scanner` 调用而将定义改名，导入失败。`unittest` 的 `util.three_way_cmp`／`case.TestCase` 属同类运行风险。

## 修订

- 直接传入带 `__init__.py`、明确使用自身包名且不使用平级模块导入的包目录时，规划模块名包含包名；绝对包内导入进入兼容性检查。兼有平级导入的目录保持原有平级解释，以免破坏脚本入口。默认构建警告明确指出产物可能在运行时失败，并提示运行 `--check`。
- 新的显式开关 `--preserve-unproved-module-attributes`，或 YAML `obfuscation.preserve_unproved_module_attributes: true`，在目录规划中对已识别、无法证明可改写的项目模块属性重新规划，保留对应导出名称。警告列出保留名称。默认仍为关闭，以保持旧产物命名契约。缓存签名包含这个选项。
- 这个模式减少相关导出名的混淆，不声称覆盖动态/未知模块身份、所有反射或运行时猴子补丁。外部使用的公开 API 名称仍需按需加入 `exclude_names`，并对最终产物做原文/产物行为差分。

## 验证

- 最小循环导入包：默认规划报告 1 个未证明站点，`--check` 给出具体建议；显式开启保守模式后报告 0 个剩余改名失配站点，独立子进程导入并调用返回 `7`。
- Python 3.15 原生环境：`json/` 保留 `dump/dumps/load/loads/make_scanner` 后，产物导入并执行 `json.dumps({'x': 1})` 成功；`unittest/` 保留 11 个已识别名称后，产物导入且 `unittest.TestCase` 可访问。两项均在全新产物路径的独立 Python 3.15 进程运行，不等于其完整标准库测试套件通过。
- 本地相关跨文件测试及 Core 全套结果随本分支 PR/CI 记录；Windows/macOS 和 3.9–3.15 全矩阵由 PR CI 验证。没有做新的 Pro L3 或冻结包适配声明。

下一步：若保守模式在真实包上仍留有未证明站点，继续用最小复现补检测或给出明确跳过；不要以 `module_attribute_accesses_unproved == 0` 单独证明所有动态访问安全。P1 打包交付按 [功能路线](ROADMAP.md) 独立验证。
